# C8 사전등록 — 2차 분석 (작성: 2026-10-31, 실행 전)

## 지위
confirm·select·dev는 이미 다른 분석에서 열람했으므로, C8은 **확증 실험이 아니라 사전등록된 2차 분석**이다. 논문에서도 그렇게 구분해서 보고한다. 설정값은 C4와 동일(v1 추출기, λ=1.0, BM25 k1=1.5, b=0.75, 사이트당 최대 100문항).

## 목적: 심사 패턴별 구멍 막기
| 구멍 | 분석 |
|---|---|
| 평가 도구 신뢰성: 메인 결과가 동점 처리에 기대는가? | E3-R |
| 예산 효율과 K 선택 | E3-K |
| λ를 골라서 좋은 결과가 나온 것인가? | E3-L (train만) |
| 독창성: 그냥 문맥 확장 아닌가? | E1-B |
| 주장 범위 | E4 |

## E3-R 동점 처리 (해석적 계산, 표본 오차 없음)
- **R0** 문서 순서 동점 처리 (C4 H1 재현)
- **R1** 무작위 동점 처리의 기댓값: fusion − shuffled, Recall@30
- **R2 (보수적)** fusion은 동점에서 항상 지고, shuffled는 항상 이기는 경우의 차이
- 판정: R1·R2 모두 사이트 군집 CI 하한 > 0 이면 "H1은 동점 처리에 의존하지 않음"

## E3-K 예산
Recall@{1,5,10,20,30,50,100}과 상위 k 노드의 읽기 토큰. @100에서 이득이 작으면 그대로 보고.

## E3-L λ 민감도 (train 30사이트만)
λ ∈ {0.25, 0.5, 1, 2, 4}에서 fusion − shuffled 차이. 평가 사이트에서는 λ를 바꾸지 않음.

## E1-B 문맥 확장 baseline (모두 같은 fusion 식, 같은 λ)
부모 텍스트(자기 텍스트 제외) · 앞뒤 형제 2개씩 · 태그/속성 경로(class·id·itemprop 등, 5단계) · 관계(v1) · 무작위 관계
두 가지 예산: **cap64**(모든 문맥 64토큰 상한), **matched**(노드마다 그 노드의 관계 길이로 잘라 토큰 수를 동일하게)

| ID | 비교 (Recall@30, 무작위 동점) |
|---|---|
| B1–B3 | 관계 − 부모 / 형제 / 경로, cap64 |
| B4–B6 | 같은 비교, matched |
| B7 | 부모 문맥 − BM25 (문맥 확장 자체의 효과) |

R1, R2, B1–B6에 Holm 보정 적용.

### 해석 규칙 (실행 전 고정)
- 관계가 matched에서 이기면: "같은 토큰이면 구조 관계가 일반 문맥보다 낫다" → 방법 기여
- 관계가 cap64에서는 지고 matched에서는 이기면: "관계는 토큰 효율적인 다리" → 효율 기여
- 둘 다 비슷하면: 주장을 "구조 문맥이 다리 역할을 한다"로 일반화하고, 기여는 현상의 정량화와 통제 실험(shuffled, Q-matched, 사전등록)에 둔다. **이 경우에도 그대로 보고한다.**

## E4 범위
공식 CSV에서 전체 질문 수, yes/no 답변 수, 증거 노드가 없는 질문 수, span 질문 수를 사이트별로 보고. 결론은 span 질문에만 적용됨을 명시.
